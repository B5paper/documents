# bsp note

## cache

* 我想入门 BSP，从哪开始比较好

    想入门 BSP，最有效的方式是从一块**支持完善、有现成 BSP 的开发板**开始，而不是一上来就啃启动代码和寄存器手册。核心思路是：**先“用” BSP，感受它解决了什么问题，再“读”它，最后尝试“改”它。**

    ### 🎯 路径一：从 MCU 或轻量级 RTOS 入手（最推荐初学者）

    如果你有基本的 C 语言基础，这是最容易建立信心的起点。很多现代 MCU 厂商都提供了封装好的 BSP。

    *   **具体行动**：买一块常见的入门开发板，比如 **STM32** 或 **ESP32**。不要一上来就看启动文件，直接打开厂商的 IDE（如 STM32CubeIDE）或框架（如 ESP-IDF），创建一个官方例程（比如 Blinky）。
    *   **学习重点**：观察代码中是如何调用 `BSP_LED_Init()` 或直接操作 `led1_on()` 这类函数的。你会发现，BSP 帮你封装了“引脚是哪个、时钟怎么开、驱动能力设多少”这些琐碎的细节。你的任务是**看懂 BSP 提供的接口**，并尝试用这些接口写几个简单的外设控制程序。
    *   **为什么从这里开始**：ESP32 和 STM32 的社区资料极其丰富，遇到问题容易搜索到答案。像安富莱等论坛也有专门的 BSP 驱动开发视频教程，跟着学上手很快。

    ### 🐧 路径二：从嵌入式 Linux 入手（需要一定基础）

    如果你已经熟悉 Linux 命令和 C 语言，可以挑战更复杂的系统级 BSP。

    *   **具体行动**：选择一款资料多的 Linux 开发板（如正点原子的 I.MX6U-ALPHA）。按照教程，从“**BSP 工程管理实验**”开始。
    *   **学习重点**：这时的 BSP 不仅仅是驱动，还包含**引导程序（Bootloader）** 和**内核启动参数**。你需要理解 BSP 是如何整理工程目录、编写通用的 Makefile 来编译出最终固件的。Yocto Project 的文档里也详细介绍了 Linux BSP 的层（Layer）结构，可以作为深入学习的参考。

    ### 🛠️ 路径三：从理解概念和阅读源码入手

    无论选择哪条路，最终都要落到代码上。BSP 的本质并不神秘，它只是**把板级相关的配置打包成了函数**。

    *   **阅读官方 BSP 源码**：找一个你手上开发板的 BSP 包，打开它的源码看。你会发现里面其实就是在调用底层的 HAL（硬件抽象层）函数来 `Output::new()` 或者配置 I2C 速率，只是它把这些操作固定在了特定的引脚上。
    *   **理解 BSP 的“边界”**：当你需要快速做原型时，用 BSP；当你需要非默认的引脚配置或想学习底层原理时，就应该绕过 BSP，直接使用 HAL 或寄存器。

    **总结一下**：找一块流行的开发板，**先用 BSP 点个灯**，体会它带来的便利；然后**打开它的源码**，看看它在背后做了什么；最后尝试**修改它的配置**，把灯换到另一个引脚上。这个“用-读-改”的过程，就是最好的入门。

* 我想入门 kmd，应该怎么办

    入门 KMD（内核模式驱动程序）和入门 BSP 的路数很不一样。BSP 通常有现成的板子和教程，试错成本低；而 KMD 开发的是运行在系统内核里的代码，**没有内存保护，一个指针写错就可能直接蓝屏**，风险高得多。

    所以，最稳妥的路径是：**先把环境搭对，然后用微软官方的“Hello World”模板跑通全流程，建立信心后再去啃内核基础。**

    ### 🛠️ 第一步：搭好环境，这是硬门槛

    KMD 开发不能像写应用那样随便找个编辑器。你需要一套特定的工具链，官方推荐的是 Visual Studio + WDK 的组合。

    *   **安装 Visual Studio 2022**：在安装时，工作负载要选择 **“使用 C++ 的桌面开发”**。这还不够，最关键的是在“单个组件”标签页里，**务必勾选“Windows 驱动程序工具包 (WDK)”**。没有这个，你的 VS 里就不会出现驱动程序的项目模板。
    *   **调试工具**：安装 WDK 时会包含 Windows 调试工具（WinDbg），这是后续调试内核代码的必备品。
    *   **准备一台测试机**：**不要在你的日常开发机上直接安装和测试驱动**。驱动一旦崩溃会直接带走整个系统。标准做法是准备一台虚拟机（如 VMware/Hyper-V）作为“目标计算机”，通过网络调试来部署驱动。

    ### 📝 第二步：跑通第一个 KMDF 驱动

    环境就绪后，不要一上来就去研究 `IRQL`、`IRP` 这些概念。先用微软官方模板，感受一下 KMDF（内核模式驱动程序框架）的骨架。

    *   **创建项目**：在 VS 中新建项目，选择 **“内核模式驱动程序，空 (KMDF)”** 模板。驱动名称建议简短些，有 32 字符的长度限制。
    *   **关键文件**：新建后会自动生成 `Driver.c` 文件（注意是 `.c` 不是 `.cpp`）。你需要在这个文件里实现 `DriverEntry` 和 `EvtDriverDeviceAdd` 这两个核心回调函数。
    *   **编译观察**：直接生成解决方案，你会得到一个 `.sys` 文件和一个 `.inf` 文件。`.sys` 就是驱动本体，`.inf` 是告诉 Windows 如何安装它的说明书。

    这一步的目的不是让你理解每一行代码，而是让你亲眼看到：一个能跑在内核里的二进制文件是怎么被生产出来的。

    ### 📚 第三步：补上内核开发的“生存常识”

    当你跑通模板后，再回过头看文档，你会发现有些概念如果不搞懂，寸步难行。

    *   **IRQL（中断请求级别）**：这是内核开发最重要的概念之一。简单说，它规定了你的代码在什么“紧急程度”下运行。在 `PASSIVE_LEVEL` 可以随便调函数、访问分页内存；但到了 `DISPATCH_LEVEL` 或更高，如果你碰了分页内存，系统立刻蓝屏。**如果你没有线程上下文、中断优先级这些概念，开发 KMD 几乎是不可能的**。
    *   **WDF 与 WDM**：你入门用的 KMDF 是微软为了降低门槛推出的框架。它把电源管理、即插即用这些极其繁琐的逻辑都封装好了，你只需要填设备特定的业务逻辑。用 KMDF 写出来的代码量通常只有老式 WDM 的 1/2 到 1/3。所以，**入门阶段死磕 KMDF 就好，不要去看 WDM**。

    ### 🚀 进阶方向（如果你想深入）

    如果你跑通了 Hello World，并且想往更硬核的方向走，可以关注这两块：

    *   **安全方向**：KMD 是 EDR（端点检测与响应）、反作弊系统的核心战场。你需要学习更底层的机制、未公开的 API，以及如何使用 Driver Verifier、GFlags 等工具排查问题。
    *   **图形驱动**：显卡厂商实现的 KMD 是另一个复杂的子系统，它通过 Dxgkrnl 与系统交互，处理显示端口驱动程序的接口。这属于非常专精的领域，通常需要硬件厂商的文档支持。

    总的来说，KMD 入门的关键是**敬畏心 + 工具链**。先不要急着写功能，先用官方模板把“编译-部署-调试”这个循环跑通，知道自己写的代码一旦出错会以什么形式崩溃，然后再慢慢深入。

* 我想入门 linux 的 kmd

    入门 Linux 内核模块（KMD）开发，和之前聊的 Windows KMD 相比，最大的不同是：**Linux 内核是开源的，你不需要等待厂商提供框架和文档，整个生态本身就是最好的教材。**

    最稳妥的路径是：**先在用户空间把环境准备好，然后用一个“空模块”跑通加载和卸载流程，建立信心后再去啃字符设备驱动。**

    ### 🔧 第一步：准备编译环境（Linux 下更简单）

    Linux KMD 本质上就是一个个 `.ko` 内核模块文件。你不需要像 Windows 那样折腾 Visual Studio 和 WDK，只需要在终端里装好编译工具和当前内核的头文件：

    ```bash
    # Ubuntu / Debian 系
    sudo apt update
    sudo apt install build-essential linux-headers-$(uname -r)
    ```

    装完后用 `uname -r` 确认一下版本，你的模块必须和当前运行的内核版本完全一致才能加载。这一点比 Windows 省心很多，没有复杂的证书签名问题。

    ### 📝 第二步：从“Hello World”空模块跑通全流程

    这是 Linux 驱动开发的经典起点。一个合法的内核模块**至少需要三样东西**：加载入口、卸载出口、许可证声明。

    创建一个 `hello_world.c`：

    ```c
    #include <linux/module.h>
    #include <linux/kernel.h>

    static int __init helloworld_init(void)
    {
        printk(KERN_INFO "Hello, Linux Kernel!\n");
        return 0;  // 返回 0 表示加载成功
    }

    static void __exit helloworld_exit(void)
    {
        printk(KERN_INFO "Goodbye, Linux Kernel!\n");
    }

    module_init(helloworld_init);
    module_exit(helloworld_exit);
    MODULE_LICENSE("GPL");
    ```

    配套的 `Makefile` 几乎是固定模板，告诉内核构建系统你有一个外部模块要编译：

    ```makefile
    obj-m += hello_world.o

    all:
        make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

    clean:
        make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean
    ```

    执行 `make` 后你会得到 `hello_world.ko`。然后：

    ```bash
    sudo insmod hello_world.ko    # 加载
    dmesg | tail                  # 应该能看到 "Hello, Linux Kernel!"
    sudo rmmod hello_world        # 卸载
    dmesg | tail                  # 应该能看到 "Goodbye, Linux Kernel!"
    ```

    **这一步的目的不是理解每一行代码，而是让你亲眼看到：一个内核模块是如何被“插入”到运行中的内核里，又安全地被“拔出”的。** 这和 Windows 驱动需要两台机器调试的痛苦体验完全不同，你在自己的开发机上就能完成整个循环。

    ### 📚 第三步：进入字符设备驱动（这才是真正的“驱动”）

    空模块只会打印日志，没有实用价值。Linux 驱动分为**字符设备、块设备、网络设备**三大类，新手应该从**字符设备**入手。像键盘、鼠标、串口、LED 控制这类“按字节流读写”的设备，都是字符设备。

    一个字符设备驱动的骨架包含几个关键部分：

    1. **设备号**：内核用 `dev_t` 来标识每个设备，分为主设备号（对应哪个驱动）和次设备号（对应具体哪个设备）。
    2. **`file_operations` 结构体**：这是驱动和用户空间之间的“桥梁”。你在这个结构体里填入 `open`、`read`、`write`、`release` 等函数指针，用户程序对 `/dev/xxx` 文件的读写操作，最终就会落到你写的这些函数上。
    3. **注册与注销**：用 `register_chrdev` 或更现代的 `alloc_chrdev_region` + `cdev_add` 来注册设备，卸载时用对应的函数释放资源。

    用一个极简的例子感受一下核心逻辑：

    ```c
    static struct file_operations hello_fops = {
        .owner = THIS_MODULE,
        .open  = hello_open,
        .read  = hello_read,
        .write = hello_write,
    };
    ```

    用户空间执行 `cat /dev/hello` 时，内核就会调用你写的 `hello_read`；执行 `echo "data" > /dev/hello` 时，就会调用 `hello_write`。**驱动开发的核心工作，就是把硬件的行为“翻译”成这些标准的文件操作接口。**

    ### 🧭 后续路线

    跑通字符设备后，你的路线可以这样推进：

    - **`ioctl`**：因为 `read`/`write` 只能传数据流，控制类命令（如设置波特率、查询状态）需要 `ioctl` 来传递结构化参数。
    - **并发与互斥**：内核代码可能被多个进程同时调用，你需要学习自旋锁、互斥体来保护共享数据。一本以 Linux 5.10 为蓝本的《Linux内核模块开发技术指南》对此有系统讲解。
    - **平台设备与设备树**：如果你最终想驱动真实的硬件（比如 ARM 开发板上的外设），`platform_driver` 和 Device Tree 是绕不开的，它们负责把硬件资源（引脚、中断号、寄存器地址）告诉驱动。
    - **中断处理**：当硬件需要主动通知 CPU 时（比如按键按下），你需要注册中断处理函数。

    Linux KMD 入门最好的“老师”其实是**内核源码本身**。当你对某个 API 的用法有疑问时，直接去 `drivers/` 目录下看类似的驱动是怎么写的，往往比任何教程都直接。

* 再往后呢，该学什么

    跑通字符设备后，接下来最该学的就是 **platform 总线模型 + 设备树**。这是从“虚拟驱动”走向“真实硬件驱动”的分水岭，也是现代 Linux 驱动（尤其是 ARM 嵌入式方向）的标准写法。

    ### 🧱 核心必学：Platform 总线与设备树

    你之前写的字符设备，设备号是手动指定的，硬件资源也是写死在代码里的。但真实的 SoC（比如 ARM 芯片）里，有成百上千个内部外设，它们**不挂在 I2C/SPI 这类物理总线上**，没法被内核自动探测。为此，Linux 创造了 **platform 虚拟总线**来统一管理它们。

    这个模型的核心是把“设备”和“驱动”分开：
    *   **`platform_device`**：描述“硬件有什么”（寄存器地址、中断号、DMA 通道等）。
    *   **`platform_driver`**：描述“怎么驱动它”，核心是 `probe()` 函数，当驱动和设备匹配成功时，内核就调用 `probe` 来初始化硬件。

    匹配的过程靠的是**设备树（Device Tree）**。硬件信息不再写死在 C 代码里，而是写在 `.dts` 文件中，由 bootloader 传给内核。驱动通过 `of_` 系列函数从设备树节点里读取寄存器地址、中断号等资源，实现了“一份驱动代码适配多种板子”的解耦。

    ### 🧠 同步机制：并发与竞争

    内核是多线程并发的，你的驱动很可能被多个进程同时 `open`、`write`，或者被中断打断。如果不做保护，数据就会错乱甚至崩溃。

    你需要掌握内核提供的同步原语，根据场景选择：
    *   **自旋锁（spinlock）**：适用于**极短**的临界区，且不能睡眠的场景（如中断上下文）。
    *   **互斥体（mutex）/ 信号量**：适用于临界区可能**睡眠**的场景（如需要等待 I/O）。
    *   **原子操作 / RCU**：用于特定高性能场景的无锁算法。

    ### ⚡ 中断处理：上半部与下半部

    真实硬件会通过中断“通知” CPU。但中断处理函数（上半部）要求**极快返回**，不能做耗时的事情（如拷贝大量数据、等待内存分配）。

    所以 Linux 把中断拆成两半：
    *   **上半部（顶半部）**：注册 `request_irq` 的那个函数。只做最紧急的事（如读取硬件状态、清除中断标志），然后**把耗时的活儿“推迟”出去**。
    *   **下半部（底半部）**：处理被推迟的工作。常用的有 **tasklet**（在软中断上下文，不能睡眠）和 **工作队列（workqueue）**（在进程上下文，**可以睡眠**）。

    选哪个取决于你的“下半部”能不能睡眠。如果需要在里面调用可能阻塞的函数（如 `copy_to_user`、`msleep`），就用工作队列。

    ### 🧭 后续深入方向

    掌握以上三点后，你已经具备编写一个完整平台设备驱动的能力了。再往后，通常有两种深入路线：

    *   **跟着总线走**：学习 **I2C、SPI** 等真实物理总线的驱动框架。它们的模型和 platform 总线类似，但底层通信有专门的 API（如 `i2c_transfer`）。
    *   **跟着子系统走**：如果对具体硬件类型感兴趣，可以深入 **Input 子系统**（按键、触摸屏）、**IIO 子系统**（ADC 传感器）、**GPIO 子系统**等。这些子系统提供了统一的用户空间接口，让你的驱动能直接被标准应用使用。

    如果想系统性地补课，可以参考以 Linux 5.10 或 6.1 LTS 为蓝本的书籍，比如《Linux内核模块开发技术指南》或《深入Linux Kernel程式設計》，它们对上述并发、中断、Platform 等主题有连贯的讲解。
