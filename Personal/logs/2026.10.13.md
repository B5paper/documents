* 为什么 find ./ -name *common.h* 没有搜.出来 common.h

    ```bash
    $ find ./ -name *common.h*
    ./sipu_common.h
    $ find ./ -name common.h*
    ./spdlog/common.h
    ```

    **原因：Shell 通配符展开（globbing）**

    问题出在 **shell 先于 `find` 处理了 `*common.h*`**，而不是 `find` 本身。

    **详细过程**

    在 `~/proj/sdk/2610092012/include` 目录下，实际存在 `sipu_common.h`，所以：

    ```bash
    find ./ -name *common.h*
    ```

    Shell 看到 `*common.h*`（**没有引号**）时，会先在**当前目录**做 glob 匹配：

    - 当前目录里有 `sipu_common.h` → 匹配 `*common.h*` ✅
    - 当前目录里没有 `common.h`（它在 `spdlog/` 子目录下）→ 不参与当前目录的 glob

    于是 `*common.h*` 被 shell 展开成了 `sipu_common.h`，真正执行的命令变成：

    ```bash
    find ./ -name sipu_common.h
    ```

    结果自然只有 `./sipu_common.h`。

    **为什么第二条能成功**

    ```bash
    find ./ -name common.h*
    ```

    当前目录里**没有**文件匹配 `common.h*`（`sipu_common.h` 不匹配，因为它以 `sipu_` 开头），所以 shell 保留原样把 `common.h*` 传给 `find`，`find` 就正确地在子目录里找到了 `./spdlog/common.h`。

    **正确写法**

    给模式加引号，阻止 shell 展开：

    ```bash
    find ./ -name '*common.h*'
    ```

    这样无论当前目录里有什么文件，模式都会原样传给 `find`，结果就会包含：

    ```
    ./sipu_common.h
    ./spdlog/common.h
    ```

    **小技巧**

    以后用 `find -name`、`grep`、`rsync` 等带通配符的场景，**一律加引号**，就能避免这类“找不到文件”的坑。

* ctags + vim, 使用 ctrl + ] 跳转后，出现

    ```
    E433: No tags file
    E426: Tag not found: sipu_dbg_core
    Press ENTER or type command to continue
    ```

    这是为什么？之前已经设置了:set tags=./tags

    你遇到的 `E433: No tags file` 和 `E426: Tag not found` 错误，说明 Vim 在按下 `Ctrl+]` 时，**没有找到 `tags` 文件，或者找到了但其中没有你正在查找的符号**。虽然你设置了 `:set tags=./tags`，但问题可能出在路径、文件生成或符号匹配上。

    **🔍 原因分析**

    1.  **`./tags` 路径的相对性**：`:set tags=./tags` 中的 `./` 是相对于**当前编辑文件所在的目录**，而不是 Vim 的工作目录（`pwd`）。如果你在项目子目录中打开文件，Vim 只会在该子目录下找 `tags`，而不会去项目根目录找。

    2.  **`tags` 文件未生成或位置不对**：`ctags` 命令需要在项目根目录执行才能生成包含所有文件的 `tags` 文件。如果未生成，或生成在了别处，Vim 自然找不到。

    3.  **符号未被收录或格式不匹配**：
        *   `ctags` 默认可能不索引某些类型的符号（如变量、宏等）。
        *   对于 C++ 函数，`ctags` 生成的标签名可能不带 `()`，而 Vim 查找时可能带了括号，导致匹配失败。
        *   符号名中可能包含 Vim 默认不视为标识符部分的特殊字符（如 `!` 或 `[`）。

    4.  **`tags` 选项被覆盖**：如果你在多个配置文件中（如 `~/.vimrc` 和 `~/.gvimrc`）设置了 `tags`，Vim 只会采用最后加载的那个设置，可能导致你的设置被覆盖。

    **🛠️ 解决方案**

    **方案一：让 Vim 向上搜索 `tags` 文件（推荐）**

    这是最省心的方式。设置 `tags` 选项使用 `;` 进行向上搜索，Vim 会从当前文件目录开始，逐级向上查找，直到找到 `tags` 文件或到达根目录。

    在 `~/.vimrc` 中添加：

    ```vim
    set tags=./tags;/
    ```
    `;` 表示向上搜索，`/` 表示搜索到文件系统根目录。这样无论在项目的哪个子目录，Vim 都能找到根目录的 `tags`。

    **方案二：检查并重建 `tags` 文件**

    1.  **确认生成位置**：确保在**项目根目录**下执行了 `ctags -R .`。

    2.  **验证文件内容**：用 `:echo readfile('tags')` 检查 `tags` 文件是否可读，或直接在终端查看 `tags` 文件内容，确认目标符号（如 `sipu_dbg_core`）是否在其中。

    3.  **使用增强选项重建**：如果符号存在但跳转失败，可以尝试用更全面的选项重新生成：
        ```bash
        ctags -R --fields=+l --extras=+q .
        ```
        `--fields=+l` 添加语言信息，`--extras=+q` 为标签名添加限定符（如 `class::method`），有助于更精确的跳转。

    **方案三：排查 `tags` 选项是否被覆盖**

    在 Vim 中执行 `:set tags?` 查看当前生效的值。如果发现不是你设置的值，请检查 `~/.vimrc` 和 `~/.gvimrc` 文件，确保 `tags` 选项只在一处设置，或确保后加载的配置是你期望的。

    **方案四：处理特殊符号匹配**

    如果错误信息中的标签名包含特殊字符，可能需要调整 Vim 的 `iskeyword` 选项，将相关字符纳入标识符范围。

    ```vim
    " 例如，将 ! 和 [ 添加到关键字字符中（请根据实际情况调整）
    set iskeyword+=!,[
    ```

    修改后，Vim 就能将包含这些字符的符号视为一个完整的标签进行查找。

    **💎 总结**

    你遇到的核心问题很可能是 **`./tags` 的相对路径限制**。建议优先采用**方案一**，将 `tags` 选项改为 `set tags=./tags;/`，这能解决大多数子目录跳转失败的情况。如果问题依旧，再依次检查 `tags` 文件本身和符号匹配的细节。
